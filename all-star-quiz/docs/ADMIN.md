# 管理者とホストの権限

管理者は問題を管理するアカウント、ホストは参加者のうち特定ルームの進行を担当する人。管理者であるだけではルーム進行権限を持たず、ホストであるだけでは問題を編集できない。

## 管理者の初回作成

DBの管理権限を持つ運用者だけが、ローカル環境に `ADMIN_EMAIL` と12〜128文字の `ADMIN_PASSWORD` を設定して `npm run admin:create` を実行する。同じメールアドレスが存在する場合は作成を拒否し、既存パスワードを上書きしない。実行後はADMIN_PASSWORDを環境から削除する。シード・リポジトリに共通管理者パスワードを含めない。

ブラウザーからの管理者登録APIは提供しない。`/admin/login` でログインし、`/admin` で管理メニューに入る。未認証で `/admin` に直接アクセスしてもログインへリダイレクトする。

## 認証

パスワードはランダムソルト付きscrypt（N=32768, r=8, p=1）で保存する。セッションは256-bitランダムトークンで、DBはSHA-256ハッシュのみ。Cookieはquiz-admin、HttpOnly・SameSite=Strict・HTTPS時Secure・8時間の絶対期限。ゲストCookieと分離する。

5回のログイン失敗で対象アカウントを15分ロックする。成否の詳細・アカウントの存在・パスワードハッシュはクライアントに返さない。ログアウトはそのセッションをDBから削除し、他のタブも以降のAPIアクセスで失効する。Admin.enabled=falseにすると既存の全セッションも認証されない。

## サーバー側の境界

- `adminProcedure` は毎回DBの管理者セッション・有効期限・enabledを確認し、問題管理操作に使用する。
- `hostProcedure` はゲストセッションと対象ルームのホスト所属を確認する。別ルームのホスト・一般参加者は拒否する。
- 実際のゲーム更新では #11でトランザクション内でもホストとversionを再確認する。権限確認と更新の間でホストが変わる競合を防ぐ。
- 問題編集APIは #8、編集画面は #21、進行API／画面は #11・#22 でこれらの境界に接続する。
- 管理メニューは30秒ごととウィンドウ復帰時に認証状態を確認し、期限切れならログインへ戻す。データAPI自体はポーリング間隔に関係なく毎回認可する。

検証: `npm run check`。管理者・未認証・一般参加者・別ルームのホスト、期限切れ・無効化・ログアウト・連続失敗を実DBのテストで確認する。
