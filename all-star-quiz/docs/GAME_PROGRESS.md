# ゲーム進行

`games.status({ code })` は参加者に進行情報（gameId、phase、version、問題番号、開始・締切時刻）だけを返します。問題や正解の配信はIssue #15の公開状態に統合します。

ホストは `games.command({ gameId, requestId, expectedVersion, action })` を送ります。requestIdはUUID、actionはstart/next/cancelです。部屋の行ロック内で認可・期待version・状態を検証し、同じ操作の再送には保存した結果を返します。同じrequestIdで異なる操作はREQUEST_CONFLICT、古いversionはSTALE_VERSIONです。

開始には2〜20人、空でない出題セット、最後だけが最終問題であることが必要です。参加者の生存状態を初期化し、問題番号・サーバー開始時刻・10秒後の締切をDBへ保存します。開始後の新規参加は拒否します。次問へ進めるのはresultsだけです。中止は未終了状態からfinished/cancelledへ進み、終了状態は変更しません。

常駐通信プロセスは250msごとにDB上の未終了ゲームを確認します。締切到達または全生存者の回答が保存済みならplayingからclosingへ一度だけ遷移します。DB時刻を再読込するため、タイマーを失う再起動にも対応します。`closeQuestionIfReady` は回答受付・退出と同じトランザクションからも呼べます。回答の保存と締切直前の受付順はIssue #12で実装します。

判定処理用の `completeQuestion` はclosingから通常問題のresults、最終問題のfinished/final_question、生存者0人のfinished/all_eliminatedへ遷移します。通常・最終問題の実際の脱落判定と結果保存はIssue #13/#14でこの処理を呼び出します。それまではワーカーはclosingで判定を待ちます。

開始後の `games.leave({ gameId })` は記録を残して生存者をleftで脱落させます。ホストは未退出者の参加順で引き継ぎ、全員退出ならall_leftで終了します。作成から24時間経過したゲームはexpiredで終了します。

Socket.IOの接続をDBに記録し、5秒ごとに生存確認を更新します。1人の複数タブを別接続として扱い、最後の接続が切れてから30秒はホストを保持します。その後、接続中の未退出者の参加順で権限を渡します。候補なしなら保留し、元ホストが復帰しても権限を巻き戻しません。プロセス異常終了時は最大15秒の接続期限で切断を検知し、そこから猶予を計測します。一時切断だけでは脱落させません。

検証: 同一／異なるrequestIdの競合、ホスト認可、最少人数、不正セット、締切の二重処理、全員回答、通常→次問→最終終了、中止、退出、複数タブ、切断猶予、復帰、接続期限切れ、ゲーム期限切れ。
