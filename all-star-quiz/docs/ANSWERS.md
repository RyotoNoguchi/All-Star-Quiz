# 回答受付

HTTPは `answers.submit({ gameId, questionId, requestId, choice })`、Socket.IOは `SUBMIT_ANSWER({ questionId, requestId, choice }, ack)` を使います。questionIdは公開問題のID、requestIdはUUID、choiceはA〜Dです。本人はセッションから、Socket.IOの部屋は接続チケットから解決します。クライアント指定の回答時刻・参加者IDなどは拒否します。

本人への応答はrequestId、questionId、choice、answeredAt、responseTimeのみです。正誤や他人の回答は含めず、部屋へのブロードキャストもしません。

## 受付と締切

PostgreSQL内の短い部屋別受付ゲートでAnswerSubmissionを保存し、DB時計のミリ秒時刻と原子的な受付連番を採番します。時計が逆行しても、同じゲームの過去の受付時刻より前には戻さず、同一時刻は受付連番で順序を確定します。ゲームの処理用行ロックとは分けているため、回答の確定処理が遅れても先に受付を記録できます。出題開始・締切も同じDB時計で決定します。受付ゲートに入る前のネットワーク・接続取得待ちは回答時間に含みます。

確定処理はゲームの行ロックを取得して受付ゲートを閉じ、保存済みの未処理回答を連番順に処理します。その後に全員回答／締切を判断します。締切直前に受付済みだった回答を、DB処理が締切後になったことだけを理由に拒否しません。受付区間は `[startedAt, deadlineAt)` です。

参加状態・生存状態・現在の問題・受付時刻を確認し、Answerと本人用の応答を同じトランザクションで保存します。正誤の計算にはゲーム開始前に固定した問題コピーを使います。回答時間が同じ場合に使う受付連番も保持します。

## 再送と復旧

同じ本人・ゲーム・問題・requestId・選択肢の再送には、締切後でも保存済みの応答を返します。同じrequestIdで選択肢を変えるとREQUEST_CONFLICT、別requestIdで回答済みの問題へ再回答するとALREADY_ANSWEREDです。

受付後にプロセスを失っても、常駐ワーカーが未処理の受付を復旧します。中止後などの受付も拒否結果として確定し、残したままにしません。部屋削除時には受付記録も削除します。

テストは締切直前／ちょうどの境界、処理ロック中の独立した受付、保存遅延、同時送信、同一時刻の順序、再送と変更拒否、所属・脱落・別問題の拒否、プロセスを失った後の復旧、HTTP入力検証、Socket.IOの部屋固定と本人限定応答を扱います。
